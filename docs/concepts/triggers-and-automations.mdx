```bash tab="Trigger"
# One request sends one email, now.
curl -X POST https://senlo.io/api/triggered \
  -H "Authorization: Bearer $SENLO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "id": 12, "to": "ada@example.com", "data": { "resetUrl": "https://app.example.com/reset/abc" } }'
```

```bash tab="Automation"
# One event starts every active automation listening for it.
curl -X POST https://senlo.io/api/events \
  -H "Authorization: Bearer $SENLO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "event": "trial_started", "email": "ada@example.com", "metadata": { "plan": "trial" }, "payload": { "trialEndsAt": "2026-12-01" } }'
```

## Triggers

A **trigger** sends one template to one recipient when your code calls [`POST /api/triggered`](../api/triggered.mdx). It sets the From name and From email, the default template and the [locale templates](./templates.mdx#locales).

The recipient does not have to be a contact. Nothing is stored about them except the delivery log entry.

Use a trigger when your code knows exactly which email to send and when: password resets, receipts, invitations, magic links.

## Automations

An **automation** is a workflow drawn in the automation builder. It starts with a trigger node that listens for one event name from [`POST /api/events`](../api/events.mdx), and runs for one contact. The run keeps a copy of the event that started it.

| Step | What it does |
| --- | --- |
| **Send email** | Sends a trigger's template to the contact, in the contact's locale. The template sees the contact and the event's `payload` as `{{event.*}}` ([merge tags](./merge-tags.mdx#automation-emails)). |
| **Wait** | Waits a number of minutes, hours or days, or **until a date** read from the trigger event or the contact, with an offset ("3 days before `trial_ends_at`"). |
| **Condition** | Takes the **yes** or **no** branch. **Rules** check the contact, the trigger event, the contact's history and earlier emails without any code of yours; **Call my API** posts the contact and the trigger `event` (`{ name, payload }`) to your URL, and a `200` means **yes**. |
| **Wait for event** | Waits until the contact does an event (**yes**) or a time passes (**no**). If they already did it since the run started, it takes **yes** at once. The event's `payload` is this step's output for later rules. |
| **Update contact** | Merges fields into the contact's metadata (tags are added, not replaced). |
| **Exit** | Ends the run. |

Events an automation can start on:

| Event | Sent when |
| --- | --- |
| `contact_added` | A contact is created. |
| `contact_updated` | Your app updates a contact. |
| `tag_added` | Your app tags a contact. The trigger can be limited to one tag. |
| any name of your own | Whatever your app reports: `trial_started`, `invoice_failed`, `project_created`. Type the name in the trigger, or pick one your app has already sent. |

An automation starts only on its own event name: an automation on `trial_started` ignores `invoice_failed`.

A trigger can also have **filters** ("Only when"): rules on the contact or the event's payload, such as "the contact's plan is pro" or "the order total is at least 100". The run starts only when they hold. This is how `contact_updated` watches one field.

### Condition rules

| Rule on | Checks | Example |
| --- | --- | --- |
| Contact | A field (`email`, `name`, `locale`, `unsubscribed`, `tags`) or an attribute from `metadata` | `plan` is `pro`; `tags` contains `beta` |
| Trigger event | A field of the event's `payload` (dots for nested ones: `order.total`) | `reason` is `too_expensive` |
| Contact history | Whether the contact sent an event, ever or in the last N days | did not do `project_created` in the last 3 days |
| Email | Whether the email of an earlier email step was opened or clicked | Welcome email was not opened |

Rules are combined with **all** or **any**, and can be grouped once ("all of: A, and any of B or C"). Numbers compare as numbers, ISO dates as dates, everything else as text without regard to case. A field that is missing only satisfies "is not set" and "is not".

History rules read the contact's event history, which is kept as long as the workspace keeps its email details; an older event does not count. Email opens are counted from the tracking pixel, so a client that blocks images never reports an open.

Only **active** automations start; a paused one ignores events, while runs already in progress go on.

### Settings

Each automation has **Settings** next to Go Live:

- **Kind.** *Transactional* (the default) is mail the contact expects from what they did: an unsubscribed or suppressed contact's emails are skipped and the rest of the run goes on. *Lifecycle* is marketing mail (win-back, nurture, upsell): such a contact leaves the automation the moment they unsubscribe or bounce, and it never starts for them. Put `{{unsubscribe_url}}` in every lifecycle email.
- **Goal.** An event, with optional filters, that means the automation did its job ("`payment_succeeded`" for a dunning flow). When the contact does it, their run ends as a success wherever it is, so no further reminder goes out. The header shows runs started and how many reached the goal (the conversion).
- **Entry.** *Again after the previous run ends* (the default), with an optional cooldown ("not again within 7 days of the last start"), or *only once per contact*.

Like a graph change, saving the settings of an active automation publishes a new version: runs in progress keep the settings they started with.

A run that is no longer wanted (the invoice got paid, the user left) is ended with [`POST /api/automations/cancel`](../api/cancel-automations.mdx).

When a step fails because something is briefly unavailable (the Condition URL times out or answers `5xx` or `429`), it is retried a few times with growing pauses. If it still fails, or fails for a lasting reason, the step's **If this step fails** setting decides: **Stop the run** (the default) or **Continue**: a Condition then takes its **No** branch, any other step is skipped and the run goes on. A run whose step is lost on a server restart is picked up again within a few minutes.

Going live, and saving an active automation, publishes its graph as a new version. New runs start on the latest version; a run in progress finishes on the version it started on, so editing a live automation never breaks a contact halfway through. Saving an active automation therefore needs a complete graph; pause it to keep an unfinished draft. While a contact has a run in progress in an automation, the same event does not start a second run for them in that automation.

Use an automation when the email depends on what the user does over time: onboarding sequences, trial reminders, a follow-up a few days after an order.

<Callout type="info" title="Cloud only">
  On senlo.io each started run counts toward the plan's monthly automation runs, and each email toward its monthly emails. A run that would go over the limit is refused with `402`. See [Errors](../api/errors.mdx).
</Callout>

## Which one

| You want to | Use |
| --- | --- |
| Send an email your code decides on, right now | Trigger |
| Send to an address that is not a contact | Trigger |
| Send a sequence, with waits | Automation |
| Branch on what the contact did or the event carried | Automation with a Condition step (rules) |
| Branch on something only your backend knows | Automation with a Condition step (your API) |
| Let non-developers change who gets what, without a deploy | Automation |

Both send through the same templates, provider, suppression list and unsubscribe links.
